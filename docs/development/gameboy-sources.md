# Game Boy Port Sources

- AI Passport BSP and project baseline: [FoloToy/ai-passport](https://gitee.com/FoloToy/ai-passport), commit `cd73a8a6f1f95e010bfd83a08e2b915e38408308`. The application, component list, partition layout, and default configuration are changed for the game port. Upstream hardware documentation remains as reference material.
- Emulator core: [psychoplath9450/SUMI](https://github.com/psychoplath9450/SUMI), commit `1a1c47c3fc4fa7a7c2d4ffba0f55e1e7dfdad1cb`. The copied `gb` headers are adapted through `components/gb_core`: Flash bank access, RAM allocation by cartridge header, ROM I/O failure reporting, and defined 16-bit instruction fetch order. Its original license is at `third_party_licenses/SUMI-LICENSE`.
- Audio synthesizer: [deltabeard/minigb_apu](https://github.com/deltabeard/minigb_apu), commit `344d9814c0d834faf1a26ec97b57bedddefed8aa`, MIT license in `components/minigb_apu/LICENSE`. The project adapts its four-channel Game Boy APU to 16 kHz mono PCM and the board's ES8311 output.
- Chinese bitmap source: [Noto Sans SC](https://github.com/notofonts/noto-cjk), SIL Open Font License 1.1 in `assets/fonts/OFL.txt`. `tools/generate_ui_font.py` creates the firmware subset in `main/ui_font.c`.
- Controller stack: [Bluepad32](https://github.com/ricardoquesada/bluepad32), commit `e9b755faabc240585da42e6d26164bb2cdd064d3`; its [BTstack](https://github.com/bluekitchen/btstack) dependency is pinned to `5d4d8cc7b1d35a90bbd6d5ffd2d3050b2bfc861c`. The included upstream BTstack patch `0002-l2cap-allow-incoming-connection-with-not-enough.patch` was applied. Local BLE setup uses active scanning and preserves Legacy Just Works bonding for gamepads. The application selects display-only IO for keyboards and displays requested passkeys. The local generic keyboard parser retains held keys across separate consumer reports; ordinary media keys are ignored, while the upstream JX-05 special parser is retained. BTstack requests no keys when bonding is disabled and intersects responder key-distribution bits with the initiator's request; this prevents waiting for keys the initiator did not request. The Xbox 1914 firmware 5.22.16.0 paired and sent gameplay input with bonding. Licenses are at `third_party_licenses/BLUEPAD32-LICENSE` and `third_party_licenses/BTSTACK-LICENSE`.
- Device-test ROM: [wyattferguson/2048-gb](https://github.com/wyattferguson/2048-gb), commit `167788105db659f2049dd2d537ee12f63d87b1e7`, MIT license. Its `2048.gb` is 32,768 bytes, SHA-256 `46F9AB6A5E9ACB81C76E9C2C6526DB1ED4E03B4FB6F36C23FB786E31F9659FC5`.
- Second device-test ROM: [splch/pirates-folly](https://github.com/splch/pirates-folly), [MIT license](https://github.com/splch/pirates-folly/blob/main/LICENSE), [rolling ROM release](https://github.com/splch/pirates-folly/releases/tag/latest). The downloaded `pirates_folly.gb` is 131,072 bytes, SHA-256 `8C1870D9102C875CE499C2C96E4E063DACC103AC5A6679C11A0C07C748B4CB85`; its header declares MBC5 with 8 KiB battery-backed RAM. The two ROMs were packed into `build/roms-two-games.bin` (167,936 bytes, SHA-256 `212A4B73F365640708CB03D372F432ACC0EE959787857F4B4B46D9A56F8CBDC7`) and written to the ROM partition at `0x310000` on COM14 with byte-for-byte readback. The ROM files remain in ignored `build/`, not committed. On-device game and save compatibility are tracked separately in `gameboy-validation.md`.
- User-provided ROM: `pokemon_blue.gb`, 1,048,576 bytes, SHA-256 `A02956BF1B3A2FC78E191347DEFDEBDFBF6F8FB7C12375A3D1417AC21E25F921`. Its checked header declares `POKEMON BLUE`, MBC3+RAM+BATTERY (`0x13`), 1 MiB ROM and 32 KiB RAM; the header checksum matches. It replaced Pirate's Folly in the ROM-only image alongside 2048. The earlier `build/roms-2048-pokemon.bin` was 1,085,440 bytes, SHA-256 `FC0FFC48ABF16CE7B13863324EB257C513B880547C3285E6FE88C8215567CE99`; COM14 Flash readback matched. These user-supplied ROM bytes stay in ignored `build/` and are not committed or redistributed. Device gameplay and save results are tracked in `gameboy-validation.md`.

The local Bluepad32 setup skips SSP and inquiry-filter commands when BR/EDR is unavailable or disabled. `HCI_Set_Event_Filter` belongs to BR/EDR inquiry filtering; see the [Bluetooth HCI specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host-controller-interface/host-controller-interface-functional-specification.html). This avoids sending opcode `0x0c05` to the BLE-only ESP32-C3. Audio uses the installed esp_codec_dev 1.6.2 ES8311 table's 16 kHz / 4.096 MHz clock pair; its table has no 14 kHz entry, and its `es8311_set_fs()` ignores the inner configuration error. The managed driver is unchanged; the application now requests a supported rate for both the boot chime and APU output. See the [upstream ES8311 implementation](https://github.com/espressif/esp-adf/blob/release/v2.x/components/esp_codec_dev/device/es8311/es8311.c); the installed pinned source is authoritative for this build.

LCD enable behavior follows [Pan Docs LCD Control](https://github.com/gbdev/pandocs/blob/master/src/LCDC.md) and [Interrupt Sources](https://github.com/gbdev/pandocs/blob/master/src/Interrupt_Sources.md): LCD-off stops PPU activity and blanks output, while CPU/timers continue; restarting begins at line zero with a blank first frame. The local core keeps the host frame budget separate from PPU phase, and advances the window row even when pixel output is skipped. This is a scanline-level approximation, not cycle-exact PPU validation.

The optional local preloaded image also uses the user-supplied Chinese editions of Pokemon Red (1,048,576 bytes) and Super Mario Land (131,072 bytes). Their cartridge details and SHA-256 identities are recorded in the [validation record](gameboy-validation.md). These ROMs and the generated preloaded image are excluded from Git and the public release flow; the default clean image contains no games.

The present integration targets ESP-IDF 5.5.3. Code origin and a successful build are not evidence of physical keyboard compatibility or acceptance of a particular game; device results are recorded separately.
