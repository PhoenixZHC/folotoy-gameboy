# Game Boy 移植验证记录

当前回退基准、游戏兼容表和验收范围见[基准验收](gameboy-acceptance.zh_CN.md)。下表保留各历史实现阶段的测量结果，旧版单项通过不代表后续每个版本都完成验收。

原型已于 2026-09-17 烧录至 COM14 上的 ESP32-C3。构建、主机和真机结果分别报告。当前构建目标为 ESP-IDF 5.5.3，使用没有官方或恢复分区的 8 MB Flash 布局。

| 上游完整验证门禁 | 受阻 | 这项历史检查时源码是无 `.git` 的归档导入，`tools/check_repo.py` 因依赖 `git ls-files` 而受阻；后来为准备发布已初始化本地仓库。默认 Bash 命令落到不可用的 WSL；另一 Bash 可启动，但 ESP-IDF 固件门禁因不支持 MSYS/Mingw 且缺少 `python3` 而停止。定向主机测试与原生 PowerShell ESP-IDF 检查已分别执行。 |

MBC3 RTC 在关机期间不推进。早期导入时，2048 +《宝可梦蓝》ROM 镜像已逐字节校验；用户在此次更新前确认《宝可梦蓝》普通存档正常。这些证据不能替代新版暂停与设置、删除存档、具体游戏的音乐听感和速度验收。

## 其他模拟器核心评估（2026-09-17）

已将 MIT 许可的 [Peanut-GB](https://github.com/deltabeard/Peanut-GB) 和 [Walnut-CGB](https://github.com/Mr-PauI/Walnut-CGB) 编进临时诊断固件，在 COM14 上运行设备已安装的 ROM。测试直接映射 Flash，每款 ROM 运行 150 个模拟帧，前 30 帧预热；不输出音频、不传输 LCD，并统计逐行绘制回调，防止把没有实际画面的快速空转误认为性能优势。这些数字只代表启动阶段，不代表实玩帧率。

两个候选核心的临时适配均无法正常推进设备中的 256 KiB《星之卡比》ROM：150 个模拟帧总共只交付 143 行画面，而正常应接近 21600 行；随后 CPU 停在 `PC=0x0038`，LCD 关闭。ROM 回调没有记录到越界读取。根因可能是核心兼容性或临时适配细节，目前尚未分离。因此，《星之卡比》表面上的约 7.5 毫秒／帧是无效结果，不能据此替换现有核心。Walnut-CGB 对设备里的《宝可梦蓝》《数码暴龙》《彩虹战士》持续输出扫描线；这尚未证明可完整游玩、声音或存档兼容。现有核心在《星之卡比》启动阶段的测试为非绘制帧约 12.4–12.7 毫秒、绘制帧约 18.5–18.7 毫秒。把 CPU 和内存总线热代码移入 IRAM、简化 DIV 计数均未得到可重复的提速，已撤回。

正式固件继续使用现有核心。复杂《星之卡比》场景能否达到原机节奏尚未通过验证，可能需要已验证兼容的新核心，或 CPU 和内存更充足的硬件。其他项目在 ESP32-S3 上的结果不能直接作为 ESP32-C3 的性能结论。

## 水平消隐等待修复（2026-09-17）

电脑诊断程序使用设备已安装的《彩虹战士》ROM，复现持续白屏：程序停在 ROM bank 1 的 `PC=0x7f27`，轮询 `STAT & 3` 等待模式 0。原核心仅在模式 3 执行可见扫描线的 CPU 指令。修复后的帧循环分别在模式 2（80 个点时钟）、模式 3（172 个点时钟）和模式 0（204 个点时钟）执行 CPU；HALT 快进最多到下一个阶段边界。指令超出阶段的时间向后续阶段和扫描线结转。这是采用固定阶段的兼容性修复，不是逐周期精确 PPU。

最小轮询回归测试在修复前失败、修复后通过。时序（轮询、正常 CPU 帧时长、HALT 帧时长）、DMG 绘制、CGB 绘制和分区布局检查通过。修复前后诊断均使用设备只读提取的 ROM，不写 ROM 或存档分区。修复后《彩虹战士》越过等待循环。《数码暴龙》在电脑端能显示标题，并响应脚本 START 输入进入后续画面，加入 APU 生成及隔帧绘制后仍可推进；用户报告的设备白屏原因尚未分离。这些检查不等于完整游戏兼容或性能提升验证。

已向 COM14 的 `0x10000` 烧录应用，esptool 哈希校验通过；启动到达蓝牙扫描。用户随后确认《彩虹战士》和《数码暴龙》均可在设备上正常游玩，本版已解决此次报告的两个白屏问题。这不等于全流程通关验证，也不代表已单独定位《数码暴龙》原白屏的根因。完整 Shell 检查因 Bash 入口指向缺少 `/bin/bash` 的 WSL 而无法运行，改用上述定向原生检查。首次镜像校验读到了旧输出文件，随后遇到相对输出路径错误；在 build 目录重新生成指定名称的完整镜像并重跑校验后通过。

首个时序修复版的实机日志记录《彩虹战士》模拟速度为 46.9～53.2 帧／秒，存在按键变化，没有显示或音频队列丢帧，但有音频任务间歇性等待下一块数据。同时发现手柄已连接时 BLE 仍持续扫描。最终版在手柄就绪后停止扫描，断开后仅在应用允许扫描时恢复（Wi-Fi 管理仍可保持扫描关闭）；请求合并后在蓝牙线程依据最新连接状态执行。最终应用已构建、合并、校验并烧录，日志显示手柄就绪、扫描状态切换和《彩虹战士》运行。扫描策略修改后的断开重连及实际提速仍待验证；这些运行不是严格的性能对照实验。

## ROM 地址缓存与原生音频优化（2026-09-17）

映射 ROM 使用两个缓存的 bank 指针，在加载 ROM、复位、导入状态和写卡带控制寄存器时刷新，避免每次 ROM 读取都重复计算分区地址；流式 ROM 继续走原路径。APU 改为以 14 kHz 直接生成每声道 234 个采样，与既有输出采样率一致，跳过逐块重采样；按墙钟调度声音的方式不变。额外测试过内联指令取数路径，核心耗时比基线增加约 18%～22%，已撤回。

COM14 自动对照使用已安装的《星之卡比》，停止 BLE 扫描，不传输 LCD、不实际播放音频。每轮新建会话运行 450 帧，统计第 150～449 帧；第 60～79 帧按 START，第 150 帧起在帧号除以 60 余数小于 15 时按 A，第 200 帧起在帧号除以 120 余数小于 80 时按右。每十帧让出一个 RTOS tick，不计入核心/APU 测量区间。以下只反映计算耗时，不代表游戏实玩帧率，也不代表音频欠载次数。

| 绘制频率 | 基线核心 微秒/帧 | 最终核心 微秒/帧：首次 / 复测 | 基线 APU 微秒/块 | 最终 APU 微秒/块：首次 / 复测 |
| --- | ---: | ---: | ---: | ---: |
| 每帧 | 15735 | 15335 / 15329 | 611 | 538 / 540 |
| 每 2 帧 | 11592 | 11103 / 11097 | 612 | 538 / 534 |
| 每 3 帧 | 10229 | 9702 / 9700 | 613 | 535 / 536 |

三组实机绘制帧序列校验值均与基线一致（`510a4dd6`、`623144cc`、`42e01764`）。电脑固定输入运行 1800 帧后，五款已安装 ROM 的最终帧缓冲也与之前一致。七组定向主机测试通过，涵盖卡带切换/复位/取数边界、PPU 时序、GB/GBC 绘制、持续音调频率、音频调度和分区布局；音频测试还在编译时检查 APU 与应用的采样率、块长度一致。最终构建前已移除开机自动基准代码；最终构建、完整镜像校验、仅应用烧录和哈希验证通过。日志保存在本地忽略目录 `build/perf_rom_*.log`。最终版实玩日志在两个十秒窗口记录《星之卡比》为 54.0 和 51.5 模拟帧／秒，显示和音频队列没有丢块。用户完成所请求的实玩测试后反馈“感觉流畅很多”，本轮改动保留；该反馈不等于复杂场景已稳定达到原机速度，也未单独确认音乐节奏变化已经消除。
