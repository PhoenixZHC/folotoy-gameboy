## Audio clock and BLE-only setup correction (2026-10-01)

The preceding 1.2 boot log exposed two independent configuration issues. The ES8311 driver in esp_codec_dev 1.6.2 has no 14 kHz / 3.584 MHz coefficient entry, and `es8311_set_fs()` discards the inner error, so the later codec-open success log did not prove clock configuration succeeded. The application now generates and outputs 16 kHz audio (267 samples per APU block), using the supported 4.096 MHz MCLK pair. Boot-chime pitch and envelope use the output rate; both tones and the roughly 0.77-second envelope are covered by host checks. This adds sample processing and small buffers relative to 14 kHz; actual complex-game performance still needs device measurement. It does not establish that this clock issue caused previously reported stutter or tempo changes.

HCI `0x0c05` is Set Event Filter, used for BR/EDR inquiry filtering; status `0x01` means Unknown HCI Command. Bluepad32 previously sent its classic setup commands on this BLE-only target. Setup now skips SSP and inquiry filtering when BR/EDR is unavailable or disabled, while still completing BLE initialization and notifying the application. Host checks exercise the actual setup source in C3 and dual-mode configurations, including runtime-disabled BR/EDR and delayed command availability. The old source fails the BLE readiness check; the corrected source passes. BLE device-name/appearance filtering and pairing security are unchanged. This failure was not evidence of failed BLE scanning, and it did not report a controller hardware failure.

## Alternative core assessment (2026-09-17)

The [Peanut-GB](https://github.com/deltabeard/Peanut-GB) and [Walnut-CGB](https://github.com/Mr-PauI/Walnut-CGB) MIT cores were compiled into temporary diagnostic applications and run on COM14 against ROMs already installed on the device. Tests used direct Flash mapping, 150 emulated frames per ROM, 30 warm-up frames, no audio output or LCD transfer, and a pixel-line callback to reject misleading speed numbers. These measurements represent startup scenes, not gameplay frame rates.

Both temporary integrations failed to progress on the installed 256 KiB Kirby ROM: across 150 emulated frames only 143 of the expected roughly 21,600 visible lines were delivered, and the CPU ended at `PC=0x0038` with the LCD disabled. The ROM callback logged no out-of-range reads. The cause may be in core compatibility or the temporary adaptation and has not been isolated. Their apparent ~7.5 ms/frame result for Kirby is therefore invalid and cannot justify replacing the working core. Walnut-CGB continued producing lines with the installed Pokemon Blue, Digimon, and Rainbow Fighter ROMs; this does not prove full playability, audio behavior, or save compatibility. The current core's Kirby startup benchmark was about 12.4–12.7 ms without drawing and 18.5–18.7 ms with drawing. Moving its hot CPU and bus methods to IRAM, and simplifying DIV-counter arithmetic, did not yield a repeatable speed gain; both experiments were reverted.

The production firmware remains on the current core. Achieving the original Game Boy tempo in complex Kirby scenes remains unverified and may require a validated replacement core or hardware with more CPU and RAM. ESP32-S3 results from other projects do not establish ESP32-C3 performance.

## HBlank polling fix (2026-09-17)

The installed Rainbow Fighter ROM reproduced a permanent white frame in a host runner: bank 1, PC `0x7f27`, polling `STAT & 3` for mode 0. Previously the core executed visible-line instructions only in mode 3. The revised frame loop executes CPU time in mode 2 (80 dots), mode 3 (172 dots), and mode 0 (204 dots); HALT fast-forward stops at the next phase boundary. Instruction overshoot is carried between phases and lines. This is a fixed-phase compatibility correction, not a cycle-accurate PPU implementation.

The synthetic polling regression failed before the fix and passed afterward. Timing (polling, active CPU frame duration, halted CPU frame duration), DMG renderer, CGB renderer, and partition-layout host checks passed. Both the original and revised runners used ROM data read from the device without writing ROM/save partitions. Rainbow Fighter progressed past its polling loop with the fix. A host run of Digimon displayed its title and progressed after scripted START input, including APU generation and alternate-frame rendering; the user's on-device white-screen symptom is not yet isolated. These checks do not establish full gameplay compatibility or a performance improvement.

The app-only image was flashed at `0x10000` on COM14 with esptool hash verification; startup reached BLE scanning. The user subsequently confirmed that both Rainbow Fighter and Digimon can be played normally on the device; the reported white-screen failures are resolved in this build. This does not establish full-game completion or isolate Digimon's original root cause. The complete shell gate could not run because the available Bash entry resolved to WSL without `/bin/bash`; targeted native checks above were used. Initial merged-image verification encountered a stale output filename, then a relative output-path error; regenerating the exact full-image filename in the build directory and rerunning the verifier passed.

Live logs from the first timing-fix build recorded Rainbow Fighter running at 46.9–53.2 emulated frames/s with input changes, no display or audio queue drops, and intermittent audio queue waits. They also exposed continuous BLE scanning after controller connection. The final build stops scanning once a controller is ready and resumes after disconnection only when the application permits scanning (Wi-Fi management can keep it disabled). Requests are coalesced and evaluated on the Bluetooth thread against current connection state. The final app was built, merged, verified, and flashed; logs show controller readiness, a scan-state change, and Rainbow Fighter execution. The scan policy's disconnect/reconnect behavior and any performance improvement remain to be validated; these runs were not a controlled performance comparison.

## Mapped ROM and native audio optimization (2026-09-17)

Mapped ROM reads now use two cached bank pointers, refreshed on ROM load, reset, state import, and mapper writes. This avoids repeating bank-address calculations for every ROM read; streamed ROM reads retain their previous path. The APU now generates 234 samples per channel at 14 kHz directly, matching the existing output rate and bypassing block resampling. Wall-clock audio scheduling is unchanged. An additional inline opcode-fetch experiment increased core time by about 18–22% versus baseline and was reverted.

Automatic COM14 comparisons used the installed Kirby ROM, stopped BLE scanning, and omitted LCD transfers and audio playback. Each run started a fresh session and executed 450 frames, measuring frames 150–449; START was held at frames 60–79, A at frames >=150 where frame modulo 60 <15, and Right at frames >=200 where frame modulo 120 <80. Every tenth frame yielded one RTOS tick, outside measured core/APU intervals. These numbers isolate compute costs; they are not gameplay FPS or a measurement of audio underruns.
